## 1. Sprint Goal

By the end of Sprint 2, a Requester using a temporary Development Requester identity can create an IT
support ticket with supporting attachments, receive a system-generated Ticket Number, find and filter
their own tickets in My Tickets, open a read-only Ticket Detail screen, and manage attachments on their
own tickets (add, download, soft-remove) — all on a consistent, responsive Zen Green interface, with the
backend enforcing that a Requester can never see or modify another Requester's data.

## 2. Stakeholder Request Interpretation

The IT department wants a working Requester-facing front door for the ticketing system before real login
exists. A Requester must be able to describe a problem (category, related system, priority, description),
attach evidence, and submit it to get an official Ticket Number back. Afterward they must be able to find
that ticket again, search/filter/sort/page through their own history, inspect a ticket's details, and manage
its attachments — without ever seeing another Requester's tickets. Because authentication is Lab 3's job,
Lab 2 simulates "being logged in" with a Development Requester Selector: a dropdown of seeded test
identities that sets the request context for the rest of the session. It is explicitly not authentication and
must be presented to the user as a testing mechanism.

## 3. Scope

### Included
- Development Requester Selection screen, selection persistence, and Change Requester action.
- Create Ticket screen and API: full field set, frontend + backend validation, system-generated
  Ticket Number, attachment upload during/after creation.
- My Tickets screen and API: Requester-owned, paginated, searchable, filterable, sortable ticket list.
- Requester Ticket Detail screen and API: read-only ticket header + attachment management.
- Attachment lifecycle: upload, metadata retrieval, download, soft removal with reason.
- Ownership enforcement on every ticket- and attachment-scoped endpoint.
- Zen Green Theme tokens and a reusable component set (form fields, buttons, badges, alerts,
  loading/empty states) used consistently across all Lab 2 screens.
- Responsive behavior at desktop / tablet / mobile per §8.7 of the labsheet.

### Excluded
- Authentication, sessions, passwords, tokens, or real role-based authorization of any kind.
- IT Staff dashboard, queue, ticket claiming/reassignment, IT Priority editing.
- Public Comments, Internal Notes, Actions Taken.
- Any status transition beyond the initial `NEW` status (no resolve/close/reopen/cancel).
- Administrator functions (user/reference-data management).

## 4. Functional Requirements

- **FR-01** The system provides a Development Requester Selection screen listing active Development
  Requesters loaded from PostgreSQL, and requires a selection before any ticket screen is reachable.
- **FR-02** The system lets a Requester create a ticket by submitting summary, description, category,
  related system, and requested priority, and returns a unique, backend-generated Ticket Number on
  success.
- **FR-03** The system lets a Requester attach up to 5 permitted files (JPG/JPEG, PNG, WEBP, PDF; ≤5 MB
  each) to a ticket, either during creation or afterward from Ticket Detail.
- **FR-04** The system lists only the selected Requester's own tickets in My Tickets, with server-side
  search, category/related-system/priority/status filtering, sorting, and pagination.
- **FR-05** The system shows a single ticket's full detail — read-only — to its owning Requester only,
  and returns a not-found response for any other Requester's ticket ID.
- **FR-06** The system lets a Requester soft-remove one of their own active attachments by supplying a
  removal reason; the attachment's metadata remains visible but its file becomes unreachable.
- **FR-07** The system presents loading, empty, no-results, validation-failure, and API-failure states on
  every screen that fetches or submits data, with form values preserved after a failed submission.
- **FR-08** The system applies one consistent Zen Green visual language (colors, spacing, field states,
  button hierarchy, badges) across the Requester Selection, Create Ticket, My Tickets, and Ticket Detail
  screens.

## 5. Business Rules

**Ticket defaults and system-generated values**
- **BR-01** The official Ticket Number is generated by the backend, in the format `TKT-YYYY-NNNNNN`
  (4-digit creation year, 6-digit zero-padded sequence reset each year), and is unique. It is generated
  inside the same database transaction that inserts the Ticket, using a `TicketCounter` row keyed by
  year, so concurrent creations cannot collide.
- **BR-02** A new Ticket begins with `currentStatus = NEW`. No other status is reachable in Lab 2.
- **BR-03** `ticketDate` (creation timestamp) is system-generated at insert time and is never client-supplied.
- **BR-04** `itPriority` is nullable at creation; it is out of scope for Requester input in Lab 2 (IT Staff
  workflow assigns it in a later lab) and is not shown as an editable field on Create Ticket.

**Requester selection and switching**
- **BR-05** Lab 2 uses a Development Requester selector instead of login. The selected identity is for
  testing only and is not authentication; the UI must label it as such.
- **BR-06** Only Requesters with `isActive = true` appear in the Development Requester selector.
- **BR-07** Changing the selected Requester immediately invalidates and reloads all Requester-scoped
  data (My Tickets, any open Ticket Detail) rather than continuing to show the previous Requester's data.
- **BR-08** The selected Requester's identity is stored in browser `sessionStorage` (not a cookie, not a
  server session) — it is scoped to the tab and cleared when the tab closes, reinforcing that it is a test
  fixture, not a login session.

**Ticket ownership**
- **BR-09** Every Ticket belongs to exactly one Requester (the one selected at creation time) and every
  Ticket-scoped or Attachment-scoped read or write is filtered by that ownership on the backend, never
  the frontend alone.
- **BR-10** A request for a Ticket ID that exists but belongs to a different Requester returns the same
  "not found" response as a Ticket ID that does not exist at all, so ownership cannot be probed.

**Search, filtering, sorting, and pagination**
- **BR-11** `GET /api/tickets` searches `ticketNumber` and `summary` (case-insensitive, substring match)
  and supports filtering by `categoryId`, `relatedSystemId`, `requestedPriority`, and `currentStatus`.
- **BR-12** Sortable fields are `createdAt`, `updatedAt`, `ticketNumber`, and `requestedPriority`; the
  default sort is `createdAt:desc`. A secondary sort by `id:desc` is always applied so that pagination
  order stays stable when the primary sort key has ties.
- **BR-13** `pageSize` accepts only `10`, `20`, or `50`; any other value, or an out-of-range `page`, returns
  `400` naming the invalid parameter and its accepted values rather than silently clamping it.

**Validation and duplicate-submission prevention**
- **BR-14** `summary` is required, trimmed, 5–120 characters. `description` is required, trimmed,
  20–4000 characters. Both limits exist so the field is long enough to be useful and short enough to
  render cleanly in a list/detail view.
- **BR-15** `categoryId`, `relatedSystemId`, and `requestedPriority` are required and must reference an
  active Category / active RelatedSystem / a valid `Priority` enum value respectively.
- **BR-16** The Submit button is disabled for the duration of an in-flight create request, preventing a
  double-click from creating two tickets from one form submission.
- **BR-17** All Create Ticket validation is enforced on the backend regardless of what the frontend
  already checked; the frontend re-states backend field errors returned in the response.

**Failure behavior and data retained after errors**
- **BR-18** If ticket creation fails for any reason (validation, network, server error), all entered field
  values remain in the form; nothing the Requester typed is cleared.
- **BR-19** If a Ticket is created successfully but a subsequent attachment upload fails, the Ticket is not
  rolled back — it keeps its Ticket Number — and the UI reports which attachment(s) failed and that they
  can be added again from Ticket Detail. See §7 (Attachment upload failure).

**Attachment upload, download, and soft removal**
- **BR-20** Allowed attachment types are JPG/JPEG, PNG, WEBP, and PDF; both file extension and MIME
  type must match one of the allowed types, since either alone can be spoofed.
- **BR-21** Maximum attachment size is 5 MB per file; maximum 5 *active* (non-removed) attachments per
  Ticket. A removed attachment does not count against the 5-active limit.
- **BR-22** Attachment removal is a soft removal: `removedAt`, `removedById`, and `removalReason` are
  set; the row and its metadata are never deleted.
- **BR-23** A removed Attachment remains visible as metadata (filename, size, uploader, removal reason,
  removal time) but its file is not downloadable or previewable; the API returns `410 Gone` for such a
  request.
- **BR-24** Only the Ticket's owning Requester may add, download, or soft-remove attachments on that
  Ticket. Soft removal requires a non-empty `removalReason` (5–200 characters).
- **BR-25** The stored filename on disk is a generated UUID plus the validated extension; the
  Requester-supplied original filename is stored only as display metadata and is never used to build a
  filesystem path.

**Inactive Requesters**
- **BR-26** An inactive Requester never appears in the Development Requester selector (see BR-06). If a
  request arrives with an `X-Dev-Requester-Id` that resolves to an inactive Requester, the API rejects it
  with `403` rather than silently treating them as active.

**Empty and no-results states**
- **BR-27** My Tickets distinguishes "this Requester has never created a ticket" (empty state, with a
  Create Ticket call to action) from "this Requester has tickets, but the current search/filters match none
  of them" (no-results state, with a clear-filters action). The two states use different copy.

**Ticket Detail access**
- **BR-28** Opening Ticket Detail for a Ticket the current Requester does not own behaves identically to
  opening a Ticket ID that does not exist (per BR-10): a not-found state, never a redirect that reveals the
  ticket exists.

**Transition to real authentication in Lab 3**
- **BR-29** The Development Requester Selector, its `sessionStorage` persistence, and the
  `X-Dev-Requester-Id` request header are all explicitly temporary scaffolding for Lab 2 and Lab 3 replaces
  them with real authentication; no password, session, or role field is added to `RequesterUser` in Lab 2
  to avoid conflicting with that future model.

### Migration decisions

Two migrations exist: `20260812134942_init` from Lab 1, and `20260824140910_lab2_ticketing` for this sprint.

- **Additive only.** The Lab 2 migration adds tables, columns, FKs and indexes; it drops nothing and
  rewrites no existing row, so it can be applied to a Lab 1 database without data loss.
- **`Category` gained `isActive`** with a `true` default rather than being made nullable, so rows that
  existed before the migration stay visible and no backfill step is needed.
- **Two named relations from `Attachment` to `RequesterUser`** (`AttachmentUploadedBy` and
  `AttachmentRemovedBy`). Prisma needs the names because one model references another twice; the
  alternative, a single `actorId` plus a role column, would have made "who uploaded this" a runtime
  filter instead of a foreign key.
- **`removedAt: DateTime?` rather than `isRemoved: Boolean`** - see the design decision below.
- **`TicketCounter` keyed by year rather than a database sequence**, because a plain sequence cannot be
  reset per calendar year without DDL, and the counter has to be updated inside the same transaction as
  the insert for BR-01 to hold.

Key relationships (Prisma): `RequesterUser 1—N Ticket`, `Ticket 1—N Attachment`, `Category 1—N Ticket`,
`RelatedSystem 1—N Ticket`, `RequesterUser 1—N Attachment` (as uploader, and separately as remover).

Indexes: `Ticket` indexes `[requesterId, createdAt]` (My Tickets default listing) and
`[requesterId, currentStatus]` (status filtering); `Attachment` indexes `[ticketId, removedAt]` (active-count
enforcement and active/removed partitioning). `Ticket.ticketNumber` and `RequesterUser.email` are unique.

**Design decision (justified, §5.2 requirement):** Soft removal is represented as a nullable
`removedAt: DateTime?` rather than a boolean `isRemoved`. This single column carries both "is it
removed" (`removedAt !== null`) and "when," so the audit trail (removal time) doesn't need a second
column, `removedAt: null` is a direct, sargable filter for "active attachments" (used both for the
5-active-attachment limit and for the My Tickets/Detail attachment lists), and the composite index
`[ticketId, removedAt]` serves both the count check and the split active/removed display without a
second index.

Full contract — every endpoint, request/response shape, status code, and error case — lives in
`docs/lab-02/api-spec.md`. Endpoints required by the labsheet:

`GET /api/categories`, `GET /api/related-systems`, `GET /api/dev-requesters`, `POST /api/tickets`,
`GET /api/tickets` (owned, paginated list), `GET /api/tickets/:id` (owned detail), `POST
/api/tickets/:id/attachments`, `GET /api/attachments/:id` (metadata), `GET /api/attachments/:id/download`,
`DELETE /api/attachments/:id` (soft removal).

Requester identity travels on every Requester-scoped request as the `X-Dev-Requester-Id` header (not a
query parameter), so it applies uniformly to GET, POST, and multipart requests alike, and so Lab 3 can
replace it with a real `Authorization` header by changing one piece of middleware rather than every
endpoint's parameter list.

## 9. Acceptance Criteria

- **AC-01** Given valid Ticket data and a selected active Requester, when the Requester submits Create
  Ticket, then one Ticket is saved with `currentStatus = NEW` and the official Ticket Number is displayed.
- **AC-02** Given no Development Requester is selected, when the user attempts to open My Tickets,
  Create Ticket, or a Ticket Detail URL directly, then the Requester Selection screen is shown instead.
- **AC-03** Given Requester B is selected, when a Ticket belonging to Requester A is requested by ID via
  the API or the URL, then the Ticket data is not returned (not-found response).
- **AC-04** Given a Create Ticket submission missing a required field, when the Requester submits, then
  a field-level validation message appears next to that field, no network request to create the ticket is
  sent, and the rest of the form's entered values are unchanged.
- **AC-05** Given the backend is unreachable, when the Requester submits Create Ticket, then a safe
  failure message is shown and every field the Requester had filled in remains populated.
- **AC-06** Given a Requester selects a 6th file to attach to a Ticket that already has 5 active attachments,
  when they attempt to add it, then the upload is rejected with a message stating the 5-active-attachment
  limit, and the existing 5 remain untouched.
- **AC-07** Given a file larger than 5 MB or of a disallowed type, when the Requester selects it for
  attachment, then the UI rejects it before upload with a message naming the specific problem (size vs.
  type) and no request is sent to the server.
- **AC-08** Given a Ticket has one active and one previously-removed attachment, when the owning
  Requester views Ticket Detail, then both are listed, but only the active one offers a working
  download/preview action; attempting to fetch the removed one's file via the API returns `410`.
- **AC-09** Given the owning Requester removes an active attachment and supplies a removal reason,
  when the removal completes, then the attachment's metadata (including the reason) remains visible in
  the UI and the active-attachment count decreases by one.
- **AC-10** Given Requester A has 3 tickets and Requester B has 1 ticket, when Requester A opens My
  Tickets, then only A's 3 tickets are listed; when the Requester is switched to B, the list reloads to show
  only B's 1 ticket.
- **AC-11** Given a My Tickets search term that matches no ticket for the current Requester, when the
  search runs, then a no-results state (not the empty-account state) is shown with a way to clear the
  search/filters.
- **AC-12** Given a Requester with zero tickets ever created, when they open My Tickets, then an empty
  state distinct from the no-results state is shown, with a Create Ticket call to action.
- **AC-13** Given more tickets than fit on one page, when the Requester changes `page` or `pageSize`,
  then the list and pagination controls update to match, and an out-of-range `page` value returns a `400`
  naming the valid range rather than an empty list.
- **AC-14** Given the Requester changes the sort control on My Tickets, when the list reloads, then it is
  ordered by the selected field, with ties broken by a stable secondary order (id desc), so re-sorting by
  the same field never visibly reshuffles tied rows.
- **AC-15** Given the Development Requester API call fails (network or 5xx), when the Requester
  Selection screen loads, then a safe failure state is shown (not a blank dropdown, not an unhandled
  crash) with a retry action.
- **AC-16** Given no active Development Requesters exist in the database, when the Requester Selection
  screen loads, then an explicit empty state is shown instead of an empty, unexplained dropdown.
- **AC-17** Given the app is viewed at desktop, tablet, and mobile widths (per §8.7), when Create Ticket,
  My Tickets, and Ticket Detail are inspected at each width, then no horizontal page scrolling, clipped
  labels, overlapping messages, or hidden buttons occur.
- **AC-18** Given a required field's control, when a screen reader or keyboard-only user inspects it, then
  the required state, its label, and any validation message are all programmatically associated with the
  control (not conveyed by color/asterisk alone).

## 11. Assumptions and Decisions

- **Ticket Number format** `TKT-YYYY-NNNNNN`, generated transactionally via a per-year `TicketCounter`
  row (BR-01). Chosen over a raw UUID or the DB's auto-increment `id` because it is human-readable,
  sortable, and still guaranteed unique and race-safe.
- **Requester identity transport**: `X-Dev-Requester-Id` header on every Requester-scoped request,
  chosen over a query parameter so it's uniform across GET/POST/multipart and maps cleanly onto a
  future `Authorization` header in Lab 3 (see BR-29).
- **Ownership-failure status**: a Ticket/Attachment belonging to another Requester returns `404`, not
  `403`, so a client cannot distinguish "doesn't exist" from "exists but isn't yours" (BR-10, BR-28). A
  removed Attachment's file returns `410` specifically, distinct from a never-existed Attachment's `404`,
  because those are different states a client may want to handle differently.
- **Attachment storage**: local disk under `server/uploads/` (gitignored) with UUID-based stored
  filenames (BR-25), acceptable for a course lab; a production system would use object storage, which is
  explicitly out of scope here.
- **Selector persistence**: `sessionStorage`, not `localStorage` or a cookie (BR-08), so the "logged-in"
  feeling resets per tab/session, reinforcing that this is a test fixture rather than a real login that should
  survive a browser restart.
- **Pagination page sizes**: fixed to `{10, 20, 50}` (BR-13) rather than an arbitrary integer, to keep the
  UI's page-size control a simple `<select>` and to bound worst-case query cost.
- **Attachment compensation strategy**: create-then-attach as two separate steps rather than one
  all-or-nothing transaction (BR-19), because a multi-file upload has multiple independent failure points
  and rolling back a successfully created Ticket because one of several files failed would discard the part
  of the submission that did succeed; the UI instead reports per-file success/failure and lets the
  Requester retry a failed file from Ticket Detail.
